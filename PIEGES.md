## 1. Stripe / Webhooks / Paiements
- **Webhook partagé** : héberger l'UNIQUE endpoint webhook Stripe côté `karma` (dispatcher par metadata), JAMAIS créer de nouvel endpoint app par app. **Réalité vérifiée 2026-07-27 (rakshak) : ce partage n'existe PAS réellement** — ~52/71 apps ont chacune leur propre endpoint local `stripe.webhooks.constructEvent`, plafond Stripe live = **16 webhooks max**, déjà saturé plusieurs fois (kaia, arogya, soma, remix, prana...). Vérifier l'état réel avant de supposer le dispatcher fonctionnel. Libérer un slot = supprimer un doublon (ex. anciens endpoints preview Vercel).
- **Idempotence event_id OBLIGATOIRE** : sans elle, replay Stripe (redelivery timeout/500) = double crédit commission/prime (vida-grow-origine, ahimsa, tejas invoice.paid). Marquer l'event "traité" **APRÈS** succès du traitement, jamais avant (sinon un crash partiel bloque le retraitement légitime — ahimsa).
- **Split 50/10/40 partout** (jamais l'ancien 4 voies type sutra 50/10/10/30, ni l'ancien 50/20/30).
- **API version Stripe** : SDK npm évolue tous les ~6 mois (basil→acacia→dahlia...), laisser TS révéler la version cible en cas d'erreur `apiVersion not assignable`. `Invoice.subscription`/`Invoice.payment_intent` supprimés en dahlia → `invoice.parent?.subscription_details?.subscription`. `current_period_end` déplacé vers `SubscriptionItem` (`sub.items.data[0]?.current_period_end`). Ou : omettre `apiVersion` pour utiliser la version par défaut du compte (prana).
- **metadata subscription ≠ metadata invoice** : Stripe ne copie JAMAIS les metadata d'une subscription vers `invoice.metadata` — les lire depuis `subscription_data.metadata` en remontant par `subscription.id` (arogya).
- **Nickname price** : pas de caractères spéciaux/parenthèses/`%` dans un nickname Stripe (encodage URL ambigu) — texte simple uniquement (arogya).
- **Race condition retraits/double-dépense** : tout debit wallet/points DOIT être une seule requête atomique (`UPDATE ... WHERE balance >= amount`, 0 rows = solde insuffisant) ou verrouillée `FOR UPDATE` — un simple `SELECT` puis `UPDATE` séparés permet un double retrait via 2 requêtes concurrentes (seva, ahimsa, tejas — confirmé par exploit réel scripté 2×).
- **Comptes de test irréalistes** : `pm_card_visa` ne peut pas être utilisé avec `confirm:true` pour simuler un remboursement E2E réel (tejas) — utiliser les payment methods de test dédiées Stripe.
- **STRIPE_SECRET_KEY en mode LIVE par défaut** : vérifier explicitement (`sk_live_` vs `sk_test_`) avant d'activer un checkout — sinon risque de facturer un vrai utilisateur en environnement de dev/staging (vida-grow-origine). Bloquer via flag `PREMIUM_CHECKOUT_ENABLED=false` tant que non confirmé.
- **`stripe.ts` importé côté client** : si le module instancie `new Stripe(...)` au niveau racine et est importé par une page `'use client'` (même juste pour lire `PLANS`), tout le SDK Stripe (+ la clé) se retrouve bundlé côté navigateur → crash `apiKey undefined`, Lighthouse Perf en chute (sanchaya, dharma, vida-spirit). Séparer strictement `lib/stripe-plans.ts` (constantes, safe client) de `lib/stripe.ts` (SDK, server-only, garde `import "server-only"`).
- **Prix dupliqués en double appel rapide** : `ensureXPrice()` sans vérification atomique crée 2 produits Stripe si appelée 2× rapidement (rakshak) — chercher par metadata unique avant de créer, ou lock applicatif.

## 2. PostgreSQL / Migrations VPS
- **Connexion directe TOUJOURS via docker exec** : `docker exec -i supabase-db psql -U supabase_admin -d postgres` — JAMAIS `psql -h localhost -p 5432` ni `-h 72.62.191.111 -p 5432` (port 5432/6543 = Supavisor pooler multi-tenant, exige un format `user.tenant_id` non documenté → `Tenant or user not found`). Confirmé sur ~15 apps (nada, vatsalya, sangha, kaia, remix, atman, vida-spirit, arogya...).
- **Ordre migrations** : créer les tables AVANT tout `REVOKE`/`GRANT ALL ON ALL TABLES`/`ALTER DEFAULT PRIVILEGES` (leçon BIJA 0004→0005→0006).
- **`uuid_generate_v4()` introuvable** : `uuid-ossp` est installé dans le schéma `extensions`, pas `public`, absent du `search_path` par défaut → soit `SET search_path TO <app>, public, extensions;` en tête de script, soit (plus simple) remplacer par `gen_random_uuid()` (natif Postgres 13+, aucune extension requise). Vu sur remix, vatsalya, yatra.
- **`gen_random_bytes()`/pgcrypto absent du search_path de `supabase_auth_admin`** : casse TOUT signup de l'écosystème (`500 Database error saving new user`) si un trigger `handle_new_user()` l'utilise sans schema qualifié — `ALTER ROLE supabase_auth_admin SET search_path = auth, extensions;` (remix, sanchaya, nada racine cause).
- **Triggers `auth.users` partagés = incident écosystème** : `auth.users` porte ~41 triggers `AFTER INSERT` (1 par app). Un seul trigger buggé (cast enum manquant, colonne inexistante, fonction indisponible) casse le signup de **TOUTES** les apps, pas seulement la sienne. Toujours vérifier avec un throwaway user AVANT de conclure "c'est mon app" (sangha, lakshmi, soma, rakshak, sanchaya — motif récurrent ×6). Nommer les triggers/fonctions avec suffixe `_<app>` pour éviter tout DROP accidentel cross-app (remix).
- **Policy RLS récursive** : une policy `EXISTS (SELECT ... FROM profiles WHERE ...)` sur la table `profiles` elle-même déclenche `42P17 infinite recursion detected in policy` — dé-référencer via une fonction `SECURITY DEFINER` ou une colonne dénormalisée (vatsalya, arogya circle_participants).
- **RLS `FOR UPDATE` sans `WITH CHECK`** : permet à un user authentifié de PATCH n'importe quelle colonne de SA PROPRE ligne, y compris des colonnes protégées (`plan`, `super_admin`, `role`) — TOUJOURS ajouter `WITH CHECK` en plus de `USING` sur les policies UPDATE (nada, arogya, sanchaya, rakshak — motif récurrent ×5+).
- **RLS activé mais 0 policy** = accès total refusé silencieusement pour tout le monde y compris service_role scoped en `authenticated` (soma profiles). Vérifier après chaque `ENABLE ROW LEVEL SECURITY` qu'au moins une policy par opération (SELECT/INSERT/UPDATE/DELETE) existe — l'oubli de DELETE laisse un `DELETE` "réussir" avec 0 ligne affectée, sans erreur (lakshmi preferences).
- **GRANT trop larges hérités** : `ALTER DEFAULT PRIVILEGES` posé une fois en P0/P1 s'applique à toutes les tables futures — vérifier qu'`anon` n'a jamais de GRANT au-delà du strict nécessaire (vridha, vatsalya, tejas).
- **`date_trunc()` en index expression** : rejeté par Postgres (`functions in index expression must be marked IMMUTABLE`, `date_trunc` est STABLE) — indexer la colonne brute et filtrer côté requête, ou utiliser une expression réellement immutable (prana, ×2 sessions différentes).
- **Colonnes GENERATED avec fonction volatile** (`AGE()` etc.) refusées — utiliser une colonne normale + trigger `BEFORE INSERT OR UPDATE` (mitra).
- **RLS policy INSERT** : `FOR INSERT USING (...)` est invalide, PostgreSQL exige `FOR INSERT WITH CHECK (...)` (mitra).
- **pgvector self-hosted** : l'extension est dans `public`, pas `extensions` — utiliser `public.vector(1536)` sans préfixe (kanti).
- **`CREATE POLICY IF NOT EXISTS`** n'existe pas en syntaxe PostgreSQL — toujours `DROP POLICY IF EXISTS` puis `CREATE POLICY` (darpana).
- **`docker compose restart <service>` NE relit PAS les env vars** (réutilise l'image/cache) — utiliser `docker compose up -d --force-recreate <service>` (ou `up -d --no-deps <service>`) pour qu'un changement `.env` VPS soit pris en compte. Motif récurrent le plus fréquent de tout le fichier (yatra, lumios, ERRORS.md racine, arogya...).
- **Colonnes/schéma halluciné vs réel** : NE JAMAIS écrire du code contre un schéma supposé — toujours vérifier `database.ts` généré ou interroger la DB réelle avant d'écrire une requête. Motif de bug le plus fréquent après PostgREST (mana ×3, forge ×3 dérive schéma complète, sarva ×5, drishti, kosha...). Toujours régénérer `database.ts` après une migration, jamais le retaper à la main.

## 3. PostgREST — schéma exposé (le piège n°1 de l'écosystème)
- **`PGRST_DB_SCHEMAS` (env/.env VPS) n'est PAS la seule source de vérité.** PostgREST self-hosted lit en réalité un **GUC au niveau du RÔLE** `authenticator` qui écrase l'env : `ALTER ROLE authenticator SET "pgrst.db_schemas" TO '...,mon_app'; NOTIFY pgrst, 'reload config';`. Sans ce GUC, `PGRST106 Invalid schema` persiste même avec `.env` correct + container recréé + `docker inspect` confirmant l'env (bija, bimba, lumios, karma, ahimsa, dharma, vatsalya, sangha, nada, rakshak — le bug le plus documenté de tout l'écosystème, confirmé sur 10+ apps).
- **Plafond ~41 schémas exposés** : dépassé (dharma/lakshmi/soma/nada renvoyaient `PGRST106` malgré présence confirmée en config). Voir Pilier 18 (architecture) pour la vraie solution à l'échelle — ne pas juste ajouter des schémas indéfiniment.
- **`.env` VPS partagé et concurrent** : plusieurs sessions Claude Code simultanées peuvent ÉCRASER l'édition de `PGRST_DB_SCHEMAS` d'une autre session en cours (arogya — schémas d'autres apps ajoutés, le sien disparu). Toujours relire le fichier juste avant de commit une modif VPS partagée.
- **Schéma listé mais jamais créé** : si un schéma figure dans `PGRST_DB_SCHEMAS` sans exister en DB, PostgREST renvoie 503 sur TOUT (schema cache fail) — toujours `CREATE SCHEMA IF NOT EXISTS` avant de l'exposer (yatra).
- **GRANT USAGE insuffisant seul** : il faut `GRANT USAGE ON SCHEMA` + `GRANT ALL ON ALL TABLES IN SCHEMA` + `ALTER DEFAULT PRIVILEGES IN SCHEMA` (pas juste RLS) pour `anon`/`authenticated`/`service_role` (yatra, lumios, arogya edge functions).
- **`SET search_path` dans un pool de connexions ne tient pas** : l'option de connexion `-c search_path=...` n'est pas honorée par le pooler Supavisor — préférer un `SET search_path` par requête ou qualifier chaque appel (dharma).

## 4. SSH / Accès VPS
- **Mot de passe : extraire avec `tr -d "'\""`** (guillemets parasites de `.env.secrets`) — sinon échec silencieux d'authentification malgré un mot de passe "correct" en apparence (ahimsa a documenté ce piège précisément).
- **Clé SSH en secours quand le password échoue** : `ssh -i ~/.ssh/purama_vps_ed25519 root@72.62.191.111` — utilisé avec succès quand `sshpass` + password échouait sur plusieurs apps (atman, satya, lumios, vida-spirit, mitra via pg-meta API en alternative).
- **fail2ban / bans temporaires fréquents** : `Connection refused` (port 22) après plusieurs tentatives — transitoire, réessayer après 10-15 min. Ne PAS conclure "VPS mort" sur un seul échec ; toujours re-vérifier avant de bloquer une session entière dessus (motif sur ~20 apps : purusha, atman, ahimsa, bija, sangha, tejas, prana, rakshak...). HTTP (443, `auth.purama.dev`) reste généralement joignable même quand SSH est banni — ce n'est PAS une panne totale du VPS.
- **Alternative sans SSH** : `docker exec` via l'API pg-meta Supabase (`https://auth.purama.dev/pg/query` avec header **`apikey: $SERVICE_ROLE_KEY`**, PAS `Authorization: Bearer`) permet d'exécuter du SQL même quand SSH est bloqué (darpana, rishi, mitra, ahimsa).
- **`psql` absent du PATH host** : toujours passer par `docker exec supabase-db psql ...`, jamais chercher un binaire `psql` sur le VPS lui-même (lumios).

## 6. Git / Repos / Secrets — LE plus gros risque de l'écosystème
- **Un repo dédié par app sous `puramapro-oss`**, jamais `matissfrasne/purama-master`, jamais d'app committée dans le monorepo parent.
- **INCIDENT MAJEUR RÉEL (2026-07-25)** : `CLAUDE-2.md`/`<APP>-BRIEF.md`/`KARMA-BRIEF.md` avec secrets LIVE (Stripe, Anthropic, OpenAI, GitHub PAT, Google OAuth, Resend, Sentry, mdp Postgres) committés ET PUSHÉS dans **49 repos privés** `puramapro-oss`. 2e vague trouvée dans des fichiers "ordinaires" non anticipés : `.claude/session_state.md`, `task_plan.md`, `progress.md`, `handoff.md`, `.claude/settings.local.json` (11 repos supplémentaires). Un commit supprimé de `main` reste accessible via des branches oubliées (`dependabot/npm_and_yarn/*` — MIDAS clé Google exposée via 10 branches distantes malgré suppression du commit sur main).
- **Prévention systématique** : `CLAUDE*.md`, `*-BRIEF.md`, `.claude/session_state.md`, `.claude/settings.local.json`, `task_plan.md`, `progress.md`, `handoff.md` → `.gitignore` dès P0/P1, AVANT le premier commit. Si déjà commité : `git rm --cached` + amend NE SUFFIT PAS si déjà pushé (branches distantes) — nécessite `git filter-repo`/purge d'historique + rotation des secrets exposés côté Stripe/Anthropic/Google/GitHub.
- **`git add -A`/`git add .` dangereux** : a aspiré un fichier `KARMA-CLAUDE.md` (89KB) non tracké par erreur, bloqué par GitHub push protection (GH013) mais seulement après coup — toujours `git add <fichiers explicites>`, jamais `-A` sur ces repos.
- **Origin mal configuré** : un repo local prototype peut avoir un `origin` pointant vers le MÊME repo `puramapro-oss/<app>` qu'un repo légitime différent — vérifier `git remote -v` avant tout push (karma-app, incident évité de justesse).
- **Repos sans historique propre** : 29+ apps sans git dédié → `git filter-repo` (préserve historique) ou `fresh init` si 0 historique exploitable → nouveau repo `puramapro-oss/<app>` + `git rm --cached` dans le parent.
- **`purama-new.sh` / scaffold** : peut écraser un `CLAUDE.md` existant en cas de `mv` sans vérification (tejas, 21591→11 octets) ; peut initialiser un `.git` imbriqué incohérent avec le pattern repo (tejas).

## 7. Auth / OAuth / GoTrue
- **`GOTRUE_URI_ALLOW_LIST` (pas `ADDITIONAL_REDIRECT_URLS` seul, les deux existent et sont facilement confondus)** : chaque nouveau schéma custom mobile (`<app>://**`) doit y être ajouté explicitement — un oubli bloque tout retour OAuth mobile silencieusement (samaya, ahimsa, atman — `ADDITIONAL_REDIRECT_URLS` est la bonne var confirmée par atman).
- **Édition `.env` VPS sans effet perçu** : même piège que PostgREST — modifier `URI_ALLOW_LIST` dans `/opt/supabase/docker/.env` peut ne rien changer si la variable réellement utilisée par le container diverge (vérifier `docker-compose.yml` + `docker inspect`, pas seulement le fichier `.env`) (samaya).
- **PKCE flow + client mismatch** : `flowType:'pkce'` figé côté client (`@supabase/supabase-js`) mais lu depuis les cookies côté serveur par `@supabase/ssr` → utiliser systématiquement `@supabase/ssr` pour le client ET le serveur, pas un mélange (sutra).
- **Route `/callback` hors du matcher public** : si `(auth)/callback/route.ts` n'est ni dans `PUBLIC_PATHS` ni exclu du matcher proxy.ts, tout visiteur SANS session qui revient d'OAuth se fait rediriger vers `/login` avant l'échange de code — motif récurrent (ahimsa, nada, rakshak middleware `/next` querystring perdu en dev Turbopack).
- **Rate limit auth contournable** : clé basée sur `X-Forwarded-For` = falsifiable côté client — toujours dériver la clé de rate-limit du `user.id` serveur, jamais d'un header client brut (jyoti, dharma, rishi `.split(',')[0]` sur proxy multiple).
- **Open redirect `?next=`** : valider que la valeur commence par `/` et PAS par `//` avant tout `router.push(next)`, sinon `?next=//evil.com` est exploitable (vida-spirit).
- **⚠️ CRITIQUE — JAMAIS `INSERT INTO auth.users` par SQL brut, service partagé par TOUTE l'écosystème** : un `INSERT` direct (seed de test, démo, migration manuelle) laisse `confirmation_token`/`recovery_token`/`email_change_token_new`/`email_change_token_current`/`email_change`/`phone_change`/`phone_change_token`/`reauthentication_token` à `NULL` au lieu de `''`. GoTrue fait planter TOUTE requête qui scanne la table `auth.users` (`/admin/users`, `/signup` — vérif doublon d'email) dès qu'UNE SEULE ligne a une colonne token `NULL`, avec l'erreur `sql: Scan error on column index N, name "<colonne>": converting NULL to string is unsupported`. Comme `auth.users` est PARTAGÉ par les ~21+ apps de l'écosystème (1 seule instance auth.purama.dev), quelques lignes de seed mal insérées cassent le SIGNUP/LOGIN de TOUTE l'écosystème, pas seulement l'app qui a semé les données (incident réel PASHU 2026-08-07, 5 lignes sur 1365 ont suffi — cf DECISIONS.md D-032). **Fix** : toujours créer un utilisateur de test via `service_role.auth.admin.createUser({ email, password, email_confirm: true })`, jamais `INSERT INTO auth.users`. **Fix curatif si déjà cassé** : `UPDATE auth.users SET <colonne> = COALESCE(<colonne>, '') WHERE <colonne> IS NULL` sur les 8 colonnes token — idempotent, sans risque. **Diagnostic** : `docker logs supabase-auth --since 20m | grep -i error` montre l'erreur exacte ; tester la vraie correction via `docker exec supabase-auth wget --post-data=... http://localhost:9999/signup` (contourne Kong, teste GoTrue directement) plutôt que via `https://auth.purama.dev` en externe (peut renvoyer 401 pour une tout autre raison de routage/clé, ne pas confondre les deux).
- **Next.js Turbopack + Tailwind config → TOUJOURS rebuild complet** (2026-08-07, PASHU): Modifier `tailwind.config.ts` (tokens, extends, theme) ou `globals.css` (@layer) n'est PAS repris par HMR (hot module reload) — les captures d'écran/vérif visuelles montrent le design AVANT le changement, même si le code source a bien été édité, créant l'illusion que le fix a échoué alors qu'il a réussi mais n'a pas été appliqué par le runtime. **Fix obligatoire** : (1) `pkill -f "next dev"` (2) `rm -rf .next` (3) restart server (4) VÉRIFIER via `curl` le CSS compilé ou via screenshot APRÈS rebuild complet, jamais avant. Preuve réelle : l'émoji 🐾 héros déjà remplacé par SVG dans le code (lignes 72-84 page.tsx), mais screenshot montre encore l'émoji car généré AVANT rebuild → captures régénérées post-rebuild montrent enfin SVG patte + bouton/badge bg-primary/bg-card fonctionnels (fond mousse visible, pastille verte badge "Vérifié PURAMA"). Ce piège a coûté un cycle diagnostic complet inutile.

## 8. Next.js / proxy.ts / routing
- **`middleware.ts` → `proxy.ts`** : Next.js 16 a déprécié la convention `middleware.ts`/`export function middleware` au profit de `proxy.ts`/`export function proxy`. Un fichier non renommé n'est simplement JAMAIS exécuté (mana, anima, lakshmi, sanchaya, soma — vérifier que le fichier s'appelle bien `proxy.ts`, sinon toutes les routes "protégées" sont exposées sans garde).
- **Whitelister systématiquement dans le matcher** (sinon 404/redirect intempestif) : `manifest.ts`, icônes PWA, `robots.txt`, `sitemap.xml`, `sw.js`, `.well-known/apple-app-site-association`, `/icon` — chaque nouveau fichier statique à la racine tombe par défaut sous le matcher générique et se fait rediriger vers `/login` pour un visiteur non authentifié (ahimsa ×4 occurrences documentées, dharma, vatsalya).
- **`useSearchParams()` sans `<Suspense>`** = build fail systématique sur Next.js 15/16 (SSG) — extraire le composant utilisant le hook dans un enfant, wrapper `<Suspense>` dans la page (motif sur ~15 apps : arogya, kanti, drishti, forge, tejas, sutra, anima, satya, vatsalya...).
- **`next.config.ts` clés supprimées en Next 16** : `eslint`/`typescript` au niveau racine du config n'existent plus (jurispurama) ; `serverComponentsExternalPackages` → renommé `serverExternalPackages` (vridha).
- **`.bin/next`/`.bin/tsc` cassés sur Node v26** : le wrapper `.bin/*` est parfois une copie fichier et pas un symlink → `require("../server/require-hook")` crash. Appeler directement `node node_modules/next/dist/bin/next build` / `node node_modules/typescript/lib/tsc.js --noEmit` (vridha, forge, vida-spirit).
- **i18n `next-intl`** : API `{ locale }` remplacée par `{ requestLocale }` depuis v3.22+/v4 dans `getRequestConfig` — un ancien pattern rend `locale` toujours `undefined` → `notFound()` déclenché sur CHAQUE route (soma, 404 site-wide). Plugin `next-intl` peut aussi injecter un alias sous `experimental.turbo.resolveAlias` incompatible avec Next 16 (`turbopack` top-level) → config introuvable (kaia).
- **API routes shadowées par le middleware i18n** : `next-intl/middleware` s'exécute en premier et peut tenter un préfixe de locale sur `/api/*` → 404 avant d'atteindre le handler réel. Ajouter un early-return explicite pour les routes API (soma).
- **Route group `(dashboard)/X`** n'ajoute AUCUN segment d'URL — les vrais chemins sont `/X`, pas `/dashboard/X` (vida-spirit, bug de nav pré-existant sur toute la sidebar).

- **Supabase typed client + custom schema** : chaque table du `Database` custom doit satisfaire `GenericTable` (`Row: Record<string, unknown>` implicite) — une `interface` nommée sans index signature résout en `never` sur `.from().insert()/.update()` (prana, smriti — ajouter `Relationships: []` explicitement sur CHAQUE table). `createServiceClient()`/client server-side doivent être typés `<Database, 'app'>` au même titre que le client browser, sinon `any` de facto invisible au typecheck (bija).

- **Stripe SDK + TS strict** : `Stripe.LatestApiVersion` retiré en v22+ — omettre `apiVersion` plutôt que deviner (prana).
- **`node_modules` binaires natifs macOS arm64 corrompus/quarantinés** (`@next/swc-darwin-arm64`, `esbuild`, `@swc/core`) après une mise à jour système ou téléchargement — `com.apple.quarantine` bloque le chargement (arogya, purama-ai) → `xattr -d com.apple.quarantine` ou `rm -rf node_modules && npm install` propre.

- **`.easignore`** : EAS archive tout le monorepo parent par défaut (git root = `purama/`) — exclure systématiquement tous les dossiers d'apps sœurs, sinon casing incohérent ou fichiers étrangers cassent le build (ojas, ahimsa).
- **`extra.eas.projectId`** doit être un vrai UUID (généré par `eas init --force`), jamais un slug placeholder — sinon "Invalid UUID appId" (ojas, vibra) ou permission denied si `owner` pointe vers un compte sans droits (ahimsa).
- **`expo-dev-client` manquant** alors que `eas.json` déclare `developmentClient: true` (ojas, ahimsa).
- **`react-native-health`/`@livekit/react-native-webrtc`** : casse fréquente sur New Architecture (RN 0.79+) — méthodes bridge supprimées, conflits `.so` Gradle, `minSdkVersion` insuffisant (ojas ×2, mitra — nécessite parfois désinstallation complète si non utilisé activement).

## 12. Sécurité / RLS / Rate-limit — motif transverse le plus critique
- **Rate limiting en mémoire sur Edge runtime** : `setInterval`/état de module ne persiste PAS entre invocations Edge — déplacer en Node.js API route (module-level Map persiste sur invocations "warm"), ou utiliser Upstash Redis réel (satya, arogya, dharma — 13 routes de mutation sans aucun rate limit trouvées en un seul audit).
- **`Upstash_*` vides = no-op silencieux** : un rate-limiter mal configuré qui échoue à l'initialisation ne throw pas forcément — vérifier explicitement que le check est actif, pas juste "présent dans le code" (arogya).
- **Headers de sécurité absents par défaut** : CSP/HSTS/X-Frame-Options/X-Content-Type-Options à vérifier explicitement sur `next.config.ts` — l'absence totale n'est jamais détectée par un build normal (dharma, vridha).
- **`Permissions-Policy` vide = désactivation totale** : `camera=(), microphone=()` désactive la feature pour TOUS les origines y compris self — utiliser `camera=(self), microphone=(self)` (vida-spirit).
- **Farming/abus par déclaration client** : toute durée/quantité auto-déclarée côté client sans vérification serveur (`durationActualSeconds`, XP, points) est un vecteur de triche — toujours recalculer/plafonner côté serveur (vatsalya).
- **RGPD "suppression" qui ne supprime rien** : `{success:true}` retourné sans DELETE réel en base — tester avec une vraie relecture après suppression, pas juste le code retour HTTP (soma, critique).
- **`export`/RGPD absent malgré CLAUDE.md** : vérifier explicitement la présence de `api/cron/account-deletion` + export de données avant de considérer une app conforme (ahimsa).

## 13. IA / Anthropic — pas des bugs de code
- **Crédit Anthropic épuisé (`400 credit balance too low`)** : dégradation gracieuse déjà en place partout où testé — NE PAS tenter de "fixer le code", c'est un blocage business (recharge compte). Documenter une fois, regrouper tous les tests IA-dépendants pour un audit groupé au rechargement (règle CLAUDE.md #16). Vu sur 15+ apps.
- **Rate limit Anthropic Tier 1** (8K tokens output/min) : un batch parallèle de traductions/générations peut dépasser largement la limite — passer en séquentiel avec backoff exponentiel (kaia translate-messages).
- **Prompt système pour contenu sensible** : la modération IA par défaut peut être trop stricte sur du contenu légitime vulnérable (partage de douleur, témoignage) — instruire explicitement l'indulgence pour la sincérité (kosha).

## 14. Design / UI / Accessibilité
- **Contraste texte/fond jamais vérifié formellement** : motif le plus fréquent d'échec Lighthouse/axe-core — texte blanc sur couleur primaire/accent souvent sous le seuil AA 4.5:1 (lakshmi, arogya, rakshak, vatsalya — vérifier le ratio réel, pas à l'œil).
- **`dark:` Tailwind suit l'OS, pas le thème app** : si l'app a un sélecteur de thème manuel, utiliser une classe conditionnelle liée au state réel, pas `prefers-color-scheme` (ahimsa).
- **Composants >5 props required** = anti-pattern CLAUDE.md — signe quasi certain d'un composant qui devrait être scindé (ahimsa FeatureCard 7 props, CollapsibleForm 8 props).
- **Boutons/liens ChatGPT-like démo** : jamais de fausses stats (10K vidéos, 2K users) ni de features listées non câblées dans le code — grep le code avant d'écrire le copy marketing (sutra, arogya, ahimsa).

## 15. Divers / process
- **`/simplify` (règle CLAUDE.md #17) trouve systématiquement des bugs réels avant merge**, pas juste du style — traiter chaque passe comme un audit de sécurité/correctness léger, pas une formalité (motif sur ahimsa, lakshmi, rakshak, purama-ai — dizaines de bugs critiques attrapés AVANT prod par cette étape).
- **Rapports de fin de session non vérifiés** : plusieurs incidents où une session a marqué une tâche ✅ sans l'avoir réellement testée en conditions réelles (déploiement jamais fait, tsc/lint faussement annoncés 0 erreur, migration faussement annoncée appliquée) — TOUJOURS re-vérifier par une commande réelle avant d'écrire task_plan.md, jamais faire confiance à un état mental (soma ×4 occurrences dans une seule app).
- **`sed`/batch en masse sans relecture** : un `sed` de conversion `<div>`→`<main>` peut casser toutes les balises fermantes internes non ciblées → JSX invalide (soma).
- **Fichiers de scaffold non nettoyés** : `create-next-app` laisse parfois un `app/page.tsx`/`app/layout.tsx` par défaut qui shadowe les vraies routes `[locale]` custom — supprimer explicitement après ajout d'i18n (soma).
